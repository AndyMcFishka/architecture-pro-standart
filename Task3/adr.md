### Решение

Клиент подаёт заявку в интернет-банке и подтверждает её СМС-кодом. Депозитный сервис сохраняет заявку и передаёт её через Kafka в АБС. В MVP условия подтверждает бэк-офис, продукт открывает АБС. Клиент получает СМС о подтверждении ставки и открытии.

#### Сервисы и интеграции

1. **Выделяем три сервиса:** депозитный, обращений и уведомлений. У каждого отдельная БД MS SQL. Используем C# и ASP.NET Core на [.NET 10 LTS](https://dotnet.microsoft.com/en-us/platform/support/policy) с поддержкой до ноября 2028 года. Стек опирается на компетенции команды интернет-банка; сервисы разворачиваем независимо от старого монолита.

2. **Онлайн-каналы вызывают сервисы по HTTPS API.** Ставки, счета и результат подачи нужны клиенту сразу. HTTPS защищает передачу данных, а API позволяет связать старую и новую платформы без общих библиотек. Для фоновой обработки используем Kafka. Ядро интернет-банка к ней не подключаем и прямые вызовы АБС в новый процесс не добавляем.

3. **Ставки и заявки храним в депозитном сервисе.** Бэк-офис ведёт общие и персональные ставки через веб-интерфейс с раздельными правами. Условия подтверждённой клиентом заявки не меняем: в АБС её можно подтвердить или отклонить.

4. **Обращения с сайта передаём в колл-центр.** Сервис обращений сохраняет контакты и продукт, затем передаёт событие через Kafka. Адаптер вызывает HTTPS API колл-центра с ID обращения. Получатель исключает дубли, адаптер подтверждает сообщение после сохранения обращения. История консультаций и существующая связь с АБС остаются в колл-центре. Подбор особых условий не меняет уже подтверждённые депозитные заявки.

5. **При сбое доставки в колл-центр повторяем отправку.** Используем задержку и ограничение нагрузки. Сообщения, которые не удалось обработать, сохраняем для разбора и повторного запуска. О проблеме сообщаем сопровождению.

6. **Список счетов показываем из локальной копии.** Депозитный сервис хранит ID счёта, владельца, валюту и статус. Клиент видит только свои счета. При недоступности АБС используем последнюю копию; ещё не загруженный счёт выбрать нельзя. Перед открытием АБС проверяет владельца, статус и средства в своей транзакции. Приём заявки не гарантирует открытие.

7. **Копию счетов обновляем из АБС.** Начальные данные загружаем порциями через API, изменения получаем через журнал событий, адаптер и Kafka. Версии записей защищают от устаревших событий. Фоновая сверка исправляет расхождения без запросов в АБС при каждом открытии формы.

8. **СМС-код создаёт и проверяет депозитный сервис.** Код связан с клиентом и условиями, действует ограниченное время и используется один раз. Число попыток ограничено. Задания на отправку кода и двух уведомлений передаём через отдельный топик Kafka.

9. **СМС доставляет сервис уведомлений.** Он сохраняет задание по уникальному ID в своей БД, затем подтверждает сообщение Kafka. Отправляет СМС через банковский шлюз и повторяет отправку при временных ошибках. Задания с истёкшим кодом не отправляет. Ответ шлюза означает приём сообщения, а не доставку клиенту. Проверка кода остаётся в депозитном сервисе; доступа к его БД у сервиса уведомлений нет. Старые вызовы шлюза сохраняем.

10. **АБС подключаем через адаптер и внутренний HTTPS API.** API предоставляет бизнес-операции и скрывает Oracle и PL/SQL. Адаптер ограничивает общую скорость и параллелизм всех своих экземпляров, включая обработку очереди после сбоя. АБС отвечает за проверки, транзакции, учёт и открытие продукта. Повторное исполнение исключает по ID заявки.

#### Быстродействие существующих платежей

В MVP включаем оптимизацию загрузки платёжных справочников (P-01 Task2). Команда интернет-банка измеряет задержки интерфейса, сервера и запросов к БД, затем устраняет найденные причины совместно с командой АБС, если требуется изменение её запросов. Способ оптимизации выбираем по измерениям; корректность и актуальность справочников сохраняются. При одинаковой нагрузке оптимизация не должна увеличивать нагрузку на АБС.

До начала работ согласуем профиль нагрузки и способ измерения отклика от запроса пользователя до отображения данных. Результат — загрузка справочников меньше секунды; перед пилотом повторяем проверку вместе с новыми депозитными сценариями. Работы и ресурсные зависимости включены в W0 плана Task4.

#### Надёжность и защита данных

1. **Сохраняем данные и событие вместе.** Для заявок, обращений и заданий на СМС используем outbox: изменение данных и запись события входят в одну транзакцию БД соответствующего сервиса. Обработчик публикует событие в Kafka и отмечает отправку после подтверждения брокера. Так принятая заявка не теряется до отправки. Повторная публикация допустима; получатели исключают повторное выполнение по ID операции.

2. **Статусы заявки применяем по порядку.** АБС записывает изменение статуса и событие одной транзакцией Oracle. У каждой заявки своя непрерывная последовательность номеров событий, начиная с 1; номер назначается в той же транзакции. Адаптер читает журнал порциями и отмечает прогресс после подтверждения Kafka. Депозитный сервис сохраняет входящие события до подтверждения Kafka и применяет только следующий номер, проверяя допустимость перехода. Обновление статуса, номера последнего применённого события и задания на соответствующее СМС в outbox атомарны. Одновременная обработка одной заявки сериализуется в БД; повторы не меняют результат и не создают новых уведомлений.

   При пропуске номера последующие события сохраняются и ждут. Адаптер восстанавливает недостающие события из журнала через существующий API АБС, порциями и с общим ограничением нагрузки. Срок хранения журнала согласуется с периодом восстановления. Если событие недоступно или переход некорректен, обработка статусов этой заявки приостанавливается и сопровождение получает оповещение; другие заявки продолжают обрабатываться. Клиент видит последнее последовательно подтверждённое состояние, которое может отставать от АБС.

   Два уведомления — о подтверждении ставки и об открытии — имеют отдельные номера 1 и 2 в рамках заявки и стабильные ID. Сервис уведомлений сохраняет задания до подтверждения Kafka и передаёт второе в шлюз только после подтверждённого приёма первого шлюзом. При перестановке заданий второе ждёт первого; незавершённая отправка повторяется, длительная задержка или постоянная ошибка вызывает оповещение и блокирует только эту пару уведомлений. СМС-код в эту последовательность не входит. Порядок фактической доставки телеком-оператором не гарантируется.

3. **HTTP-подача идемпотентна.** Отправитель создаёт ID операции до первого запроса и сохраняет его при повторах. При том же ID и данных сервис возвращает прежний результат; при других данных — конфликт. Новая подача получает новый ID. Результат храним весь допустимый период повторов из контракта API.

4. **Проверку кода и создание заявки фиксируем атомарно.** ID операции, параметры, заявка и outbox сохраняются одной транзакцией; для депозитной заявки здесь же отмечаем использование проверенного СМС-кода. Уникальность ID в БД защищает от одновременных повторов. Повтор завершённой операции возвращает результат без повторного использования кода.

5. **Проверяем права при каждом запросе.** В интернет-банке ID операции связан с аутентифицированным клиентом, на сайте — с защищённым контекстом формы. Сам ID не даёт доступа к персональным данным. API АБС требует аутентификации и разрешает только нужные операции. Доступ к топику и данным доставки ограничен отправителями и сервисом уведомлений.

6. **Шифруем данные и ведём аудит.** Трафик защищаем шифрованием, изменения ставок и статусов записываем в аудит. Содержимое кодовых сообщений шифруем также при хранении. Для него задаём короткий срок хранения и удаляем по его окончании. Чувствительные данные и коды не пишем в технические логи.

#### Размещение и резервирование

1. **Два рабочих ЦОД принимают клиентские запросы.** Каждый рассчитан на полную нагрузку. Отказоустойчивая балансировка распределяет запросы между площадками и экземплярами приложений. Проверки доступности автоматически исключают неисправные узлы. Прерванный запрос можно повторить идемпотентно.

2. **БД резервируем между рабочими ЦОД.** У БД трёх сервисов и интернет-банка есть основные и синхронные резервные реплики. Автоматическое переключение возможно только на синхронизированную реплику при наличии кворума. Исключаем одновременную запись на двух основных узлах; без кворума запись принудительно не включаем.

   В штатном режиме подтверждаем запись после устойчивого сохранения в обоих рабочих ЦОД. При отказе одного ЦОД допускаем аварийный режим: после подтверждения кворума и исключения записи на недоступном узле актуальный узел оставшейся площадки подтверждает локально устойчивую запись без ожидания отсутствующей реплики. При потере резервного ЦОД основной узел переходит в этот режим по тем же правилам. Переход сопровождается оповещением.

   Вернувшийся узел не принимает запись до синхронизации с действующим основным. После синхронизации восстанавливаем подтверждение записи в обоих ЦОД. Механизм перехода и восстановления проверяем отдельно для каждой СУБД. При потере оставшейся площадки до восстановления репликации возможна потеря данных, принятых в аварийном режиме (риск 4).

3. **Третья площадка обеспечивает кворум и репликацию Kafka.** На ней размещаем свидетель кластера БД, контроллер и брокер Kafka. Контроллеры и реплики сообщений распределяем по трём площадкам: RF=3, min.insync.replicas=2, acks=all.

4. **Третьей площадкой может быть облако.** Оно должно быть независимо от двух рабочих ЦОД. Полный стек приложений там не нужен. Провайдера выбираем после проверки защищённых каналов, их задержек и пропускной способности, независимости маршрутов и допустимости хранения реплик Kafka с банковскими данными.

5. **Резервируем авторизацию и СМС-шлюз.** Сессии доступны экземплярам приложений в обоих рабочих ЦОД. До запуска проверяем отказ каждой площадки, переключение БД и полную нагрузку на оставшийся ЦОД.

6. **Сайт и банковский колл-центр входят в резервирование MVP.** Их приложения работают в обоих рабочих ЦОД за отказоустойчивой балансировкой; оставшаяся площадка рассчитана на полную нагрузку. PostgreSQL колл-центра и используемые сайтом изменяемые данные и сессии резервируются между ЦОД. Для сохранения обращений и переключения БД действуют правила пункта 2. Конкретный механизм для платформы колл-центра подтверждает её подрядчик до утверждения плана.

   Разработчики сайта и подрядчик колл-центра вместе с инфраструктурной командой обеспечивают работу авторизации, конфигурации и необходимых внутренних зависимостей при потере любой рабочей площадки. Проверяем просмотр ставок и подачу обращения на сайте, доставку в колл-центр, доступ оператора к сохранённым обращениям и ставкам. Переключение не должно терять подтверждённые обращения или создавать дубли; допустимое время восстановления согласуется в рамках цели доступности 99,9%. Готовность подтверждается сквозными испытаниями до пилота, а не наличием резервной БД.

#### Кто участвует

1. **Команда интернет-банка внутри банка:** депозитный сервис и его БД, интерфейс ставок и доработки интернет-банка.
2. **Команда АБС:** API, адаптер, журнал событий, проверки, дедупликация и рабочее место бэк-офиса.
3. **Разработчики сайта:** ставки, форма обращения, вызовы новых API и работа сайта в двух ЦОД совместно с инфраструктурной командой.
4. **Подрядчик колл-центра:** API приёма обращений, дедупликация, доступность обращений оператору и резервирование платформы с PostgreSQL совместно с инфраструктурной командой.
5. **Ответственные за инфраструктуру в IT-отделе:** Kafka, эксплуатация БД, балансировка, резервирование, мониторинг и СМС-шлюз.
6. **Подрядчик интернет-банка:** сервисы обращений и уведомлений с их БД, адаптер колл-центра; консультации и изменения платформы, если возможностей команды банка недостаточно.

Разработчики сайта и инфраструктура здесь обозначены как роли: отдельных команд для них в условии нет. Ответственных нужно назначить. Команды документируют интерфейсы и вместе проверяют сквозные сценарии и отказоустойчивость. Загрузку и сроки оценивает менеджер проекта. Распределение соответствует [плану Task4](../Task4/task4-roadmap-task-details.md): для обращений и уведомлений предполагаются два состава подрядчика; их доступность и компетенции нового .NET-стека подтверждаются до утверждения плана.

### Альтернативы

1. **Обращения внутри депозитного сервиса.** Меньше компонентов, но консультации и открытие продукта оказываются в одном сервисе.
2. **Депозиты в старом монолите.** Меньше новых сервисов, но остаются ограничения платформы и общего масштабирования.
3. **Ставки в АБС.** Сотрудникам привычнее, но онлайн-каналы сильнее зависят от перегруженной системы.
4. **PL/SQL напрямую из адаптера.** Проще интеграция, но сильнее зависимость от Oracle.
5. **Фоновая доставка без Kafka, в том числе напрямую в колл-центр по HTTPS.** Меньше инфраструктуры, но нужен отдельный механизм доставки и повторов.
6. **Отправка СМС из депозитного сервиса.** Меньше компонентов, но доставка смешивается с депозитной логикой.
7. **СМС-подтверждение в ядре интернет-банка.** Можно использовать существующий механизм, но понадобится доработка подрядчика.
8. **Только кворум на третьей площадке.** Дешевле, но потеря рабочего ЦОД может остановить запись в Kafka.

**Недостатки, ограничения, риски**

1. Три сервиса, интерфейс сотрудников, Kafka и третья площадка увеличивают объём разработки и сопровождения. Срок MVP — шесть месяцев; свободные ресурсы команд ещё нужно подтвердить.
2. API колл-центра, API и журнал событий АБС нужно разработать или подтвердить их возможности. Для уведомлений нужен доступ к API банковского СМС-шлюза.
3. Версии и лицензии БД, задержки между ЦОД и резервирование старого интернет-банка требуют проверки. Совместимость старой платформы и её БД с выбранной схемой уточняем у подрядчика. Возможность резервирования сайта и платформы колл-центра, включая PostgreSQL и внутренние зависимости, также требует проверки с их владельцами. Это целевая архитектура, а не готовая инфраструктура.
4. Схема рассчитана на отказ одной площадки при исправности остальных компонентов. Доступность 99,9% подтверждаем испытаниями и мониторингом. Синхронная репликация добавляет задержку. После отказа одного рабочего ЦОД продолжаем запись на оставшейся площадке; до восстановления синхронной репликации потеря этой площадки может привести к потере данных, подтверждённых в аварийном режиме. Этот риск принимается ради продолжения работы при отказе одного ЦОД. Резервные копии нужны отдельно от репликации.
5. После неопределённого ответа СМС-шлюза возможна повторная отправка. Нужно проверить поддержку идемпотентного ID и запроса статуса. Ограничения срока действия и повторного использования кода сохраняются независимо от доставки.
